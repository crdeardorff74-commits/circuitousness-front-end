## 2026-06-22 — Pitfall: Claude Preview tool's `vh` ≠ emulated viewport
- When verifying responsive CSS in the Claude Preview tool, `vh` units compute against the tool's REAL window height, not the `preview_resize` emulated viewport — so vh-based sizes render at the wrong scale in the preview even though `matchMedia`/`innerHeight` correctly report the emulated size. Bit me during the How-to-Solve tutorial + short-landscape menu work (v0.50–0.53): a `clamp(…, 16vh, …)` thumbnail measured 62px at an emulated 390px-tall viewport because 16vh resolved against the ~657px real window.
- Workaround: for short-viewport rules that MUST be verified in-tool, use fixed `rem` (predictable in both preview and real device) — that's why the `@media (max-height:500px)` menu thumbnail is a flat `3.2rem`, not vh-based. For vh-based rules, don't trust the preview's rendered px; reason about real-device vh manually or check on a real phone.

## 2026-05-01 — Partial-redraw during rotation animation

- Old `draw()` iterated all ROWS×COLS tiles in three passes (dim channel, lit channel, walls) every frame, regardless of how few tiles were actually animating. On 15×15 a full draw measured ~31ms — below 60 fps and visibly choppy.
- Refactored: extracted body to `drawCore()` (full draw, used for initial loads, hint pulses, dramatic flash, resize, and the first frame after a rotation kick-off). Added `drawAnimatedFrame()` that only re-renders animating tiles + their 8 neighbors, clipped to the bounding box (with `0.3*cellSize` margin for the 45°-rotation overshoot). Hoisted `buildLitKeys`, `renderTileDim/Lit/Wall`, `laneIsOpposite`, `laneIsVertical` so both paths share them.

## 2026-04-28 — Two-path mode + per-path coloring + tile face alpha

- **Two-path mode** (`Maze.setTwoPathMode`, debug-panel checkbox): generates puzzles with two independent entry/exit pairs that may share cells via cross tiles. Render uses these for hint-locked pre-emptive lighting so each lane gets its own color even before the connecting chain reaches it.

Renderer's `litPalette(pathIdx)` returns gold for the just-completed path independent of the other — path 1 turns gold while path 2 is still blue, then path 2 catches up.

## 2026-04-28 — Pre-gen lookahead cache + hurry-cancel

- **Replaced single-slot pre-gen with a lookahead Map** (`PREGEN_LOOKAHEAD = 3` in `game.js`). After each puzzle loads, `fillPreGenQueue()` walks forward in the progression and queues the first missing size; each worker response chains into the next one. `newPuzzle` consumes from `preGenCache` by `"r,c"` key. Cache stays populated even when a fast hint-solver advances — buffer drains one entry per puzzle but refills as builds complete.
- **Hurry signal** for the catch-up case. `Maze.setHurry()` flips a flag init() checks at every attempt boundary, bailing with `bestState` (or current attempt's grid). Worker handler in `maze-worker.js` calls it on `{type:'hurry'}`. `newPuzzle` posts hurry only when worker is in-flight on the wanted dims; fresh builds (initial load, slider jump) just send a normal generate request.
- **Removed always-on leniency** (`skipSmartRerolls`/`skipCapShrink` past 100/200 tiles). Strict generation runs always now. Lookahead gives enough lead time even at 14×14+; hurry is the only path that can ship a sub-canonical puzzle, and only when player actually caught up. The user explicitly preferred this over global leniency.
- **Banner threshold = 500ms** with split text: "Loading…" for in-flight wait, "Building puzzle…" for fresh builds. Tiny grids never flicker; only legit long waits surface a message.
- **Debug-panel pre-gen indicator**: `Cache: 5x4 5x5 6x5 | building 7x6 (1.9s)` polls every 200ms. Shows every cached size + any in-flight build with elapsed seconds, so it's obvious when pre-gen is keeping up vs catching up.
- **maze-worker.js cache-busts its own `importScripts('maze.js')`** by reading `?t=` off its own URL. Without this, even with no-cache headers + cache-busted worker URL, a freshly-spawned worker can still latch onto a stale cached `maze.js`.
- **File:// fallback** in `ensureWorker()`: try/catches `new Worker()` (Workers can't load from file://); on failure, sets `workerAvailable=false` and `newPuzzle` builds via main-thread `Maze.init()` instead of waiting on a non-existent worker. Page works without dev server, just without pre-gen.

## 2026-04-28 — Progression mode + Web Worker pre-gen + canonical-path fix

Win-banner click / N-key triggers `Game.newPuzzle()` with no args; advance only happens when `lastWon` is true. ## 2026-04-25 — DPR fix: render in device pixels

- **The persistent "thin lines at tile boundaries inside path channels" bug ate ~10 iterations.** Root cause: Canvas anti-aliasing on non-integer DPR displays (Windows scaling 1.25/1.5). With the usual `ctx.scale(dpr)` setup, integer CSS coords land on FRACTIONAL device pixels — adjacent tiles' fillRect/stroke edges had AA-mismatched pixels at every shared boundary, showing as faint cross-channel lines. **Fix:** compute everything in device pixels (`canvas.width = grid + 2*pad` directly, `ctx.setTransform(1,0,0,1,0,0)` — no DPR scaling), force `cellSize` even, `cellAt` converts incoming CSS pointer coords to device pixels. Earlier attempts (per-cell gridline skip, channel extension by bevel-thickness, removing L/R bevel contrast, fillRect-instead-of-stroke for straights) ALL FAILED because they fought the symptom on the CSS side; only device-pixel rendering eliminates it.
- **Game now framed as a "circuit"** — entry/exit notches connect via an external connector around the grid perimeter, drawn as ONE polyline through `drawCircuitOutline` so every corner is a smooth `lineJoin='round'` bend (separate strokes had visible butt-cap seams). Lit palette is `LIT_GREEN` while in progress, flips to `LIT_GOLD` the moment `Maze.won` becomes true (single `litPalette()` drives every lit element). User mused about renaming the game to something circuit-related but didn't commit.
- **Twin locking** added — `TWIN_PAIR_COUNT` tile pairs (one path-tile + one filler each) rotate together via `_twin = { partner, color }` tags. Cross tiles deliberately excluded (4-rotation-symmetric → coupling would be invisible). Per-pair pastel palette derived programmatically from a base hex via `paletteFromBase` (additive lighten for top, multiplicative darken for bot/right). Hint-locked twins lock their partner too (with the same rotation delta) so they can't desync.
- **Cheat → Hint** rename (i18n key, button id, JS function). Hint-locked path tiles now also light their solution lane gold *before* the connecting chain reaches them — red bevel = locked, gold groove = confirmed-correct.
- **Difficulty thresholds scale with SIZE** in `maze.js`: `MIN_PATH_LENGTH = round(SIZE * 2.25)`, `MIN_PUZZLE_LENGTH = round(SIZE * 1.75)`, `MIN_SHORTCUT_TWISTS = round(SIZE * 1.25)`, `MAX_DFS_STEPS = SIZE² * 125`, `TWIN_PAIR_COUNT = max(1, SIZE−5)`. Retry counts (`MAX_PATH_GEN_TRIES`, `MAX_REROLL_ATTEMPTS`, etc.) stay constant — they tune search algorithms, not difficulty.
- **`MIN_PUZZLE_LENGTH` is on BFS shortest-*possible* path** (treats rotation as free, since the player controls it), not on the intended DFS path. Without this, a puzzle with a long intended path but a short alternative shortcut still felt trivial — the player completes the shortest path, not the DFS one. Endpoint picker now takes farthest-of-`ENDPOINT_SAMPLES=5` random configs so the BFS floor is reachable on attempt 1.
- **Right-click rotates CCW**; touch and left-click rotate CW. `contextmenu` handler suppresses the browser menu only on the canvas.
- **Path channel `pathChannel` extends endpoints by 0 px now** — earlier attempts to extend by 1 or by `b` (bevel thickness) caused visible "tabs" sticking out of cells at terminating channels. The DPR fix made those workarounds unnecessary.
